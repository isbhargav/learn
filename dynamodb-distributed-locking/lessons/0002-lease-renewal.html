A heartbeat moves the deadline

The AWS locking guide uses a periodic heartbeat to extend the lease while the holder is active. Renewal must pass two checks in the same conditional update:

  • OwnerID still equals this acquisition’s token.
  • ExpiresAt is still in the future.

The second check prevents an expired lease from being resurrected. During the expired interval, another caller could acquire the lock.

import time
from boto3.dynamodb.conditions import Attr

def heartbeat_lock(table, resource_name, owner_id, ttl_seconds):
    now = int(time.time())
    try:
        table.update_item(
            Key={"LockID": resource_name},
            UpdateExpression="SET ExpiresAt = :expiry",
            ConditionExpression=(
                Attr("OwnerID").eq(owner_id)
                & Attr("ExpiresAt").gt(now)
            ),
            ExpressionAttributeValues={
                ":expiry": now + ttl_seconds,
            },
        )
        return True
    except table.meta.client.exceptions.ConditionalCheckFailedException:
        return False

Run this periodically with a heartbeat period comfortably shorter than the lease duration. AWS’s example uses a 3-second heartbeat and a 10-second lease; those values are an illustration, not a guarantee for every workload.

A false return is a stop signal. This token no longer holds a valid lease. Stop protected work rather than continuing until release.

Why heartbeats cannot remove stale holders

A heartbeat runs in your process. If that process freezes, its heartbeat freezes too—but the rest of the system keeps moving.

TimeEventLock state
0sA acquires a 10s leaseOwner A; expires at 10s
3sA heartbeats successfullyOwner A; expires at 13s
4sA freezes; heartbeats stopNo further extension
14sB acquires the expired lockOwner B; expires at 24s
15sA resumes and heartbeatsOwner check fails

The conditional heartbeat protects B’s lock item. It does not undo work A may already have performed after resuming. That remaining resource-safety problem is why fencing matters.
