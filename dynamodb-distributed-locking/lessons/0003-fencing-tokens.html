DynamoDB distributed locking · Lesson 3

Make stale writes lose.

Issue an increasing fencing token on every acquisition, then let the protected resource reject old holders.

8 minutesPython + boto33 retrieval checks
Your win

You will be able to generate a fencing token during lock acquisition and identify the resource-side check that actually makes fencing work.

The resource must reject the past

A random OwnerID distinguishes owners, but it does not establish which acquisition is newer. A fencing token is a number that increases on every successful acquisition.

Martin Kleppmann’s locking analysis gives the key timeline: A acquires token 33 and pauses; B acquires token 34 and writes; A resumes and sends its delayed write with token 33. The resource remembers token 34 and rejects 33.

Fencing is enforced by the protected resource. Generating a token in DynamoDB does nothing unless every protected operation carries it and the resource atomically rejects tokens older than the newest it has accepted.

Increment the token inside acquisition

DynamoDB update expressions can increment a number atomically. if_not_exists initializes the counter on the first acquisition; UPDATED_NEW returns the token assigned to this winner.

import time
import uuid
from boto3.dynamodb.conditions import Attr

def acquire_fenced_lock(table, resource_name, ttl_seconds):
    owner_id = str(uuid.uuid4())
    now = int(time.time())
    try:
        response = table.update_item(
            Key={"LockID": resource_name},
            UpdateExpression=(
                "SET OwnerID = :owner, ExpiresAt = :expiry, "
                "FenceToken = if_not_exists(FenceToken, :zero) + :one"
            ),
            ConditionExpression=(
                Attr("LockID").not_exists()
                | Attr("ExpiresAt").lt(now)
            ),
            ExpressionAttributeValues={
                ":owner": owner_id,
                ":expiry": now + ttl_seconds,
                ":zero": 0,
                ":one": 1,
            },
            ReturnValues="UPDATED_NEW",
        )
        return {
            "owner_id": owner_id,
            "fence_token": int(response["Attributes"]["FenceToken"]),
        }
    except table.meta.client.exceptions.ConditionalCheckFailedException:
        return None

Pass fence_token with every protected write. The resource must compare the token and apply the write in one atomic operation; a separate “check, then write” leaves another race.

Preserve the counter on release

Lesson 1’s guarded delete is no longer suitable: deleting the item would delete the counter, allowing a later acquisition to start again at 1. Instead, release by expiring the item and removing its owner while retaining FenceToken.

def release_fenced_lock(table, resource_name, owner_id):
    try:
        table.update_item(
            Key={"LockID": resource_name},
            UpdateExpression="SET ExpiresAt = :expired REMOVE OwnerID",
            ConditionExpression=Attr("OwnerID").eq(owner_id),
            ExpressionAttributeValues={":expired": 0},
        )
        return True
    except table.meta.client.exceptions.ConditionalCheckFailedException:
        return False

Do not use TTL to delete this fenced lock item. TTL cleanup would eventually erase the counter. The acquisition timestamp may be expired, but the fencing history must survive.
