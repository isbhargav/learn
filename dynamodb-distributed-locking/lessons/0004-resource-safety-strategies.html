Choose where
correctness lives.

Select fencing, compare-and-swap, transactions, serialization, idempotency, or a best-effort lock from the guarantees your resource can actually enforce.

Your win

You will be able to choose a resource-safety strategy from a workload’s correctness needs and the resource’s atomic-operation capabilities.

Start with the failure cost

Ask what happens if two holders overlap. If the result is only duplicated cost, a best-effort lock may be enough. If the result is corrupted state or an invalid side effect, something must enforce correctness where the operation is applied.

Then ask which atomic precondition that component supports. The answer—not the lock library—determines the viable strategy.

The strategy map

StrategyUse it whenMain limitation
Native fencing The resource can reject an older token at the same time it applies a write. A repeated request with the same token may still run more than once.
Compare-and-swap The resource can accept a write only if its version is unchanged, as with S3 If-Match. It protects only writes that check the version; it does not order unrelated actions.
Atomic transaction The safety check and all protected database changes must succeed or fail together. External API calls and other outside effects are not part of the database transaction.
Single-writer gateway Every operation can go through one service that sends them to the resource in order. Every caller must use the gateway, and only one gateway may be active at a time.
Idempotent operations Retries of the same operation can reuse one key, allowing the system to return the original result. It makes retries safe, but it does not stop an older, different write from damaging newer state.
Best-effort lock Running the work twice only wastes time or money; it cannot damage data or cause invalid effects. It reduces duplicate work but does not keep data correct when overlapping work is unsafe.

Match the mechanism to the resource

S3: expected-version writes

S3 conditional writes support If-Match. Read the object and its ETag, compute the new value, then write only if that ETag is still current. A competing write changes the ETag and causes the stale write to fail. This fits read-modify-write workflows; a failed writer must re-read before retrying.

DynamoDB: conditional update or transaction

For one item, a conditional update can check the token/version and modify the data together. For several items, DynamoDB transactions provide all-or-nothing writes. Use a transaction only when the protected changes truly need one atomic commit.

External API: serialize or redesign

If an API offers neither token checks nor version preconditions, route its operations through a single-writer gateway. That gateway becomes part of your correctness boundary: every caller must use it, and its failover must not create two active writers. If you cannot guarantee that, redesign the resource protocol rather than claiming the lock alone is safe.

Idempotency is often complementary. Use it for retries inside a fencing, CAS, transaction, or gateway design. It solves repeated execution of one logical operation—not ordering between different acquisitions.

Real-life examples

StrategyExampleWhy it fits
Native fencing Several application workers can update the same inventory record. Worker A pauses, worker B takes over with a newer token, then A resumes and tries to write. The inventory store rejects A’s older token while applying the update, so A cannot overwrite B’s newer state.
Compare-and-swap Two administrators edit the same JSON configuration in S3. Each reads the file, makes changes, and writes with the ETag they originally read. The first write changes the ETag. The second write fails its If-Match check instead of silently erasing the first administrator’s changes.
Atomic transaction An order service must create an order, decrease inventory, and validate the current operation token in DynamoDB. All three changes succeed together. If inventory is insufficient or the token is stale, none of them is applied.
Single-writer gateway A legacy customer-management API has no ETags or token checks. Several internal systems need to update the same customer profile. All systems send updates to one integration service, which processes each customer’s updates in order instead of calling the legacy API directly.
Idempotent operations A checkout service sends a “create charge” request, but a network timeout hides the result. It retries with the same purchase ID as the idempotency key. The payment system recognizes the repeated purchase ID and returns the original result rather than creating a second charge.
Best-effort lock Several servers can generate the same nightly analytics report or warm the same cache, but the output is identical each time. A lock avoids most duplicated cost. Rare overlap wastes compute but produces the same correct result.

Understand each limitation

Native fencing: repeated work can still repeat

Fencing compares different lock acquisitions. It does not automatically recognize two requests from the same acquisition as duplicates.

Example: Worker A holds token 34 and sends a write. A timeout hides the result, so A retries with token 34. Both requests may be accepted because neither token is older. If repeating the write is unsafe, add an idempotency key.

Compare-and-swap: only checked writes are protected

The resource checks the version only when the writer supplies a precondition such as If-Match. A writer that omits the check can still overwrite the resource. The check also says nothing about the order of unrelated actions.

Example: Two careful editors use If-Match on an S3 configuration, but a third script uses an ordinary unconditional upload. That script can overwrite both editors’ work. Similarly, a successful configuration write does not determine when a separate notification API call occurs.

Atomic transaction: outside effects stay outside

A database transaction covers only the database operations included in it. It cannot roll back an email, payment, or third-party API call.

Example: Your transaction creates an order and decreases inventory, but the following shipping API call fails. The database commit is not undone. Conversely, if the API call succeeds and the transaction fails, the external effect remains. You need a workflow, retry, and reconciliation design for those outside effects.

Single-writer gateway: nobody can bypass it

The gateway preserves order only when every operation goes through it. Its failover must also ensure that two gateways do not become active writers at the same time.

Example: Internal systems send customer updates through an integration service, but one script still calls the legacy API directly. That direct call can overtake the gateway’s updates. During failover, an old gateway and its replacement must not both continue sending writes.

Idempotent operations: only the same operation is deduplicated

Idempotency recognizes retries that reuse the same key. It does not prove that an operation is current, and a different key is treated as a new operation.

Example: Retrying “create charge for purchase 123” with key purchase-123 is safe. However, an old profile update arriving with a new request ID can still overwrite a newer profile. That second problem needs versioning, fencing, or ordering.

Best-effort lock: overlap is reduced, not prevented

A best-effort lock can make duplicate work uncommon, but expiry, pauses, or failures can still allow two workers to run together.

Example: Two workers generating the same report only waste compute. Two workers issuing the same refund could create a serious financial error. The first workload can use a best-effort lock; the second needs a correctness mechanism such as idempotency and transactional state checks.

No viable enforcement point means no correctness guarantee. Longer leases, extra heartbeats, lock-delay, or another lock store can reduce risk, but they cannot replace an atomic resource-side precondition or a correctly serialized write path.
