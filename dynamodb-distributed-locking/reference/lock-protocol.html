DynamoDB lock protocol

The lock item and its guarded transitions. A lease coordinates callers; it does not by itself fence a stale holder from an external resource.

Lock item

AttributePurpose
LockIDPartition key identifying the protected resource.
OwnerIDUnique token for one acquisition, not merely a process name.
ExpiresAtNumeric Unix epoch seconds after which another caller may acquire.

Acquireattribute_not_exists(LockID) OR ExpiresAt < :now
RenewOwnerID = :owner; extend only your own lease.
ReleaseOwnerID = :owner; never release unconditionally. A fenced design expires the item and retains its counter.

Conditional failure is expected contention. Convert ConditionalCheckFailedException into “not acquired” or “not released”; handle other AWS errors separately.

TTL is cleanup, not a lock clock. DynamoDB deletes expired TTL items eventually, typically within a few days. Acquisition must test ExpiresAt directly. If the item stores a fencing counter, preserve that item rather than deleting it through TTL. See the TTL documentation and Lesson 3.

An expired holder can still be running. After another caller takes over, the old holder may touch the protected resource unless that resource rejects stale work. Production designs need a fencing strategy where the resource cannot otherwise make operations safe.
